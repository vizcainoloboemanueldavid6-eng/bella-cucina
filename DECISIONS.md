# Decisions

Every judgement call the specification left open, and why it went the way it did. Ordered roughly
from "affects the whole project" to "affects one component".

## Project setup

**The site lives in `bella-cucina/`, a subfolder of the working directory.**
The working directory already held an unrelated Python project. A Next.js app needs to own its
`package.json`, `node_modules` and `tsconfig.json`, so it got its own folder rather than being
merged into someone else's.

**Node.js and Git were installed, because neither was on the machine.**
Node 24.21.0 (LTS) and portable Git 2.55.0 were unpacked into `C:\Users\vizca\tools\` and added to
the user `PATH`. Nothing was installed system-wide and nothing needed administrator rights.

**Next 15.5, React 19.3, Tailwind 3.4 — not the newest of each.**
At the time of writing npm offers Next 16.3, Tailwind 4.3, TypeScript 7.0 and ESLint 10. The
specification asks for "Next.js 14+" and for `npm run build` and `npm run lint` to pass cleanly, so
the stack was pinned to the combination with the most mileage behind it: Next 15.5 (App Router,
`output: 'export'`), React 19.3, Tailwind 3.4 (config-file based, so the palette lives in
`tailwind.config.ts` where a client can find it), TypeScript 5.9 and ESLint 9 with flat config.
Upgrading later is a `package.json` edit, not a rewrite.

**`npm run lint` runs `eslint .`, not `next lint`.**
`next lint` is deprecated in Next 15 and removed in 16. `eslint.config.mjs` extends
`next/core-web-vitals` and `next/typescript` through `FlatCompat`, so the rules are identical and
the script survives the next major upgrade.

## Images and media

**Plain `<img>` instead of `next/image`.**
`output: 'export'` forces `images.unoptimized: true`, which turns `next/image` into an `<img>` with
extra runtime and a less direct grip on `loading` and `fetchPriority`. Since every asset is already
resized and compressed at build time, the component buys nothing. `@next/next/no-img-element` is
switched off in `eslint.config.mjs` with a comment saying why. Every image carries explicit
`width`/`height` so nothing shifts while it loads.

**Ten Unsplash photographs, re-encoded to WebP under 200 KB each.**
Downloaded at source resolution, cropped with a saliency-aware crop and re-encoded with `sharp`,
stepping the quality down until each file fit the budget (the hero needed q68 at 1920×1280; most
others stayed at q80). The ten full-size files come to ~1.35 MB, and their generated variants add
about 1.2 MB of smaller alternatives that only one of is ever downloaded. Credits are in
`CREDITS.md`. The internet was available, so no CSS-gradient placeholders were needed.

**Every photograph ships a `srcset`, generated by a script that is in the repository.**
The first measurement of the finished page was Lighthouse mobile 70, and the reason was a single
line: the hero was a 1920×1280 file being handed to a 375px phone, which put Largest Contentful
Paint at 6.5 s. `npm run images` (`scripts/images.mjs`) now writes `-480`, `-768`, `-1200` and
`-1600` siblings for every photograph, and `src/lib/images.ts` assembles the `srcset` from the same
width list. Shipping the script matters: without it the README's "drop a WebP in `public/images`"
instruction would have produced a `srcset` full of 404s the first time anyone followed it.

**The hero offers 480, 1200 and 1600 — no 768.**
It is `object-cover` behind a full-height section, so on a tall phone it fills a box roughly three
times taller than it is wide: far more image than the honest `100vw` in its `sizes` can express.
Declaring the true requirement (`150vh`) sends every phone to the 1920px file. Instead the 768
candidate is simply not offered, so a common 1.75× phone lands on the 1200px file, encoded at a
lower quality so it still weighs 64 KB. Measured against the 768 candidate on the same machine, it
costs 0.1 s of LCP and about half a Lighthouse point, and the hero stops being visibly upscaled.

**There is no hand-written hero preload.**
One was added and then removed: React 19 already emits `<link rel="preload" as="image">` for an
`<img>` carrying `fetchPriority="high"`, so the explicit link only put a second, identical record
in the exported HTML.

**`package.json` carries a modern `browserslist`.**
Chrome 111 / Edge 111 / Firefox 121 / Safari 16.4 and up. It stops the build shipping transpiled
fallbacks and polyfills for browsers this site's visitors are not using, and those are the
versions where everything the page relies on — `:focus-visible`, `text-wrap`, `svh` units,
container-free `@media` ranges — is already supported natively.

**`public/og.jpg` is generated, not photographed.**
A 1200×630 card built locally with `sharp`: the hero photo darkened and blurred, a gold rule, and
the restaurant name set in a serif. `favicon.svg`, `apple-touch-icon.png` (180×180) and
`icon-512.png` are generated the same way from a terracotta "B".

**Fonts are self-hosted.**
`next/font/google` downloads Playfair Display and Inter at build time and serves them from the same
origin. The deployed site makes no request to Google, which is one less third-party connection for
both privacy and Lighthouse.

## Content

**The phone number is a reserved fiction number: +1 (212) 555-0148.**
555-01xx numbers exist precisely so that made-up businesses do not ring a real person. The
consequence is that the WhatsApp deep link demonstrates the flow but will not reach an account —
WhatsApp will say the number is invalid. Putting a plausible non-555 number there would have meant
pointing a public demo at a stranger's phone. To make it live, change the `WHATSAPP_NUMBER`,
`PHONE_E164` and `PHONE_DISPLAY` constants at the top of `src/config/site.ts`; every link, greeting
and piece of structured data is built from them, so nothing else needs to move.

**The address is invented, but the coordinates are real.**
184 Vincenzo Lane does not exist. The map is centred on Hudson Square in Manhattan so the
OpenStreetMap embed shows a plausible neighborhood instead of the middle of the ocean.

**Reviews, menu, prices and the family history are all invented.**
The reviews carry the required "Sample reviews for demo purposes" line, and the footer carries
"Demo project — Bella Cucina is a fictional restaurant." on every page view.

**`site.seo.url` is a placeholder.**
It is set to `https://bella-cucina.vercel.app`. Canonical URL, Open Graph URLs, the sitemap and the
JSON-LD all derive from it, so changing that one line after the first deploy fixes all of them.

## Behaviour

**Scroll reveals are armed by a `js` class, not by the component.**
An inline, render-blocking script in `layout.tsx` adds `js` to `<html>`, and `globals.css` hides
`.reveal` elements only under `.js`. Without it, a visitor with JavaScript disabled would get a page
of invisible sections. With it they get the plain document, and everyone else gets the animation
with no flash of unstyled content.

**`prefers-reduced-motion` is honoured twice.**
Globally, `globals.css` neutralises transitions, animations and smooth scrolling. Locally,
`useInView` reports "visible" immediately and the About counters jump straight to their final value
instead of counting.

**Reservation date bounds are set after mount.**
The page is statically exported, so computing "today" during render would bake the build date into
the HTML and mismatch on hydration. `min`/`max` are applied in an effect, and the past-date rule is
re-checked on submit so the validation does not depend on the attribute.

**The booking form cannot submit until React has taken over.**
It is a client-side form: the handler builds a WhatsApp message and opens it. Left alone, the
browser would happily submit it as a plain GET before hydration or with scripting off, putting the
guest's name and phone number into the URL bar and the browser history for nothing. The submit
button is therefore `disabled` until an effect has run, and `noValidate` is applied only once
hydrated so the browser's own validation covers the gap.

**The footer's opening hours are derived, not written out.**
It used to list "Tue – Thu" and "Fri – Sat" as literals, which silently assumed those days always
share a closing time. It now walks `site.hours` and starts a new row whenever the hours change, so
giving Thursday a later close produces a correct footer instead of a wrong one.

**The copyright year is corrected on the client.**
A static export evaluates `new Date()` once, at build time. That year is the server-rendered
fallback — right on the day it ships and right for anyone without scripting — and a two-line client
component replaces it with the real year on mount, so a site left running for three years does not
keep announcing the year it was built.

**The reviews carousel does not autoplay.**
Four short quotes do not need to move on their own, and content that moves without being asked is a
WCAG 2.2.2 problem. Previous/next buttons, dot buttons and arrow keys drive it instead.

**The gallery uses CSS columns for its masonry.**
`columns-1 sm:columns-2 lg:columns-3` with `break-inside-avoid` gives a real masonry layout with no
JavaScript, no layout thrash and no library. The lightbox is hand-written: focus trap, Escape,
arrow keys, backdrop click, scroll lock and focus restoration.

**Opening hours never highlight "today".**
Same reason as the date bounds — a static export has no idea what day it is when it is served.

## Small things

**Brand icons are inlined.**
`lucide-react` v1 dropped Instagram, Facebook, Twitter and YouTube. `src/components/SocialIcon.tsx`
carries the four official marks as single paths; the WhatsApp mark is inlined in
`WhatsAppButton.tsx`.

**`trailingSlash: true`.**
Static hosts differ in how they resolve extension-less paths. Emitting `index.html` inside a
directory per route is the shape every one of them handles the same way.

**`sitemap.xml` and `robots.txt` come from `app/sitemap.ts` and `app/robots.ts`.**
They are generated into `out/` at build time and read their URL from `site.ts`, so they cannot drift
from the canonical tag.

**No `aggregateRating` in the structured data.**
The JSON-LD describes the restaurant, the menu and the opening hours, all of which are true of the
page. It deliberately omits an `aggregateRating`: the four reviews are invented and the page says
so, and publishing them as a 4.8-star average would hand a search engine a number no guest ever
gave. `disambiguatingDescription` carries the demo notice instead, so the fiction is machine
readable as well as visible. `sameAs` is omitted rather than emitted empty, since every social link
is a `#` placeholder.

**Contrast was raised in four places after an audit.**
The opening-hours "Closed" cell (3.85:1), the form placeholders (4.05:1), the input borders
(1.35:1, and the only thing separating a white field from a near-white card) and the filled review
stars (2.2:1) all failed WCAG AA. They now use `ink-muted`, `ink/50` and `gold-dark`. The palette
in `tailwind.config.ts` is unchanged — only the tokens chosen for those four elements.

**Playwright screenshots are checked in, as JPEG.**
`docs/` holds full-page captures at 375, 768, 1280 and 1920 px plus the two crops the README uses.
They are committed so the README renders on GitHub without anyone having to run the site. As PNG
they came to 23 MB, which is a rude thing to put in a repository someone has to clone; at JPEG
quality 82 the same six images are about 4.5 MB and no different to look at. The capture runs with
the browser locale pinned to `en-US`, or the OpenStreetMap embed renders its own chrome in whatever
language the machine taking the screenshot happens to use.

**The map in those screenshots is composited in.**
Chrome paints out-of-process iframes unreliably in a beyond-the-viewport capture, so the map lands
blank in a full-page shot. The capture script photographs the map on its own — where it renders
exactly as a visitor sees it — and pastes it back at its document coordinates.
